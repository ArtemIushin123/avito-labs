# trip-service

Сервис поездок TripGo, лабораторная работа 1: HTTP API и PostgreSQL.
Умеет создавать, получать и завершать поездку. Данные хранятся в PostgreSQL,
схема накатывается миграциями goose, код HTTP-слоя генерируется из OpenAPI.

## Требования

- Go 1.26+ (версия из `go.mod`; инструменты `oapi-codegen`, `goose`, `mockgen` ставятся в модуль, запуск через `go tool`)
- `tripgoctl` - утилита курса для локального окружения
- `golangci-lint` - отдельным бинарём, нужен только для `make lint`

## Запуск

```bash
tripgoctl cluster start          # один раз на машине
tripgoctl environment start      # поднимает PostgreSQL и создаёт .env
make migrate                     # накатить миграции
make run                         # запустить сервис
```

Makefile читает переменные из `.env.example`, а затем из `.env` поверх него.
`.env` создаёт и перезаписывает `tripgoctl` при каждом `environment start`, и в нём
нет `HTTP_*_TIMEOUT`, поэтому их значения берутся из `.env.example`, а адрес БД
с актуальным портом из `.env`. Если запускать бинарь мимо `make`, экспортируй оба файла
по очереди (сначала `.env.example`, потом `.env`).

## Переменные окружения

Все обязательные. Пример значений лежит в `.env.example`.

Сервис падает на старте с понятной ошибкой, в которой названа переменная, если:
- переменная не задана или не разбирается в нужный тип;
- любой таймаут (`HTTP_*_TIMEOUT`, `SHUTDOWN_TIMEOUT`, `DATABASE_*_TIMEOUT`,
  `DATABASE_MAX_CONN_LIFETIME`) не больше нуля;
- `DATABASE_MAX_CONNS <= 0`, `DATABASE_MIN_CONNS < 0` или `DATABASE_MIN_CONNS > DATABASE_MAX_CONNS`;
- `HTTP_ADDR` или `DATABASE_URL` пустые.

| Переменная | Назначение |
|---|---|
| `HTTP_ADDR` | адрес HTTP-сервера |
| `HTTP_READ_TIMEOUT` | таймаут чтения запроса целиком |
| `HTTP_READ_HEADER_TIMEOUT` | таймаут чтения заголовков |
| `HTTP_WRITE_TIMEOUT` | таймаут записи ответа |
| `HTTP_IDLE_TIMEOUT` | таймаут простоя keep-alive соединения |
| `SHUTDOWN_TIMEOUT` | общий бюджет на завершение процесса: остановка сервера и закрытие пула |
| `LOG_LEVEL` | читается, но пока не применяется (slog появится в работе 2) |
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `DATABASE_MAX_CONNS`, `DATABASE_MIN_CONNS` | размер пула |
| `DATABASE_MAX_CONN_LIFETIME` | время жизни соединения в пуле |
| `DATABASE_CONNECT_TIMEOUT` | таймаут подключения новых соединений пула, Ping на старте и в `/ready` |
| `DATABASE_QUERY_TIMEOUT` | таймаут обращения к БД в ручках (вся транзакция целиком) |

Четыре `HTTP_*_TIMEOUT` добавлены сверх базового набора курса: conventions
запрещают хардкодить таймауты, а ТЗ требует их выставить.

## API

| Метод | Путь | Ответы |
|---|---|---|
| POST | `/api/v1/trips` | 201, 400, 409, 500 |
| GET | `/api/v1/trips/{tripId}` | 200, 400, 404, 500 |
| POST | `/api/v1/trips/{tripId}/finish` | 200, 400, 404, 409, 500 |
| GET | `/health` | 200 |
| GET | `/ready` | 200, 503 |

Ошибки отдаются по RFC 9457 в `application/problem+json`, клиент разбирает поле `code`:
`invalid_request`, `trip_not_found`, `trip_completed`, `driver_busy`, `internal_error`.

- Текст ошибок БД наружу не уходит, он пишется в лог. Ошибки SQL в репозитории
  оборачиваются с названием операции (`create trip: add status history: ...`),
  поэтому по логу видно, где именно упало.
- Паника в обработчике перехватывается своим middleware: клиент получает `500`
  с `code=internal_error` в `problem+json`, а текст паники и стек пишутся в лог.
  Процесс продолжает работать.

## Решения

### Уровень изоляции: Read Committed

Задаётся явно при старте транзакции в `Do` (`pgx.TxOptions{IsoLevel: pgx.ReadCommitted}`).
Этого достаточно, потому что инварианты держатся не изоляцией, а самой базой:
запрет двух активных поездок держит уникальный индекс, а от двойного завершения
защищает условие в `UPDATE`. Serializable тут ничего не добавил бы, но потребовал бы
повторов при serialization failure.

### Менеджер транзакций

Интерфейс `TxManager.Do(ctx, fn)`, реализация `PgxTxManager` на pgx.

- `Do` открывает транзакцию, кладёт её в `context` под приватным ключом и вызывает
  `fn` с новым контекстом.
- `fn` вернула `nil` - `COMMIT`. Вернула ошибку или паникнула - `ROLLBACK` через `defer`,
  ошибка или паника уходят наружу. После успешного `COMMIT` отложенный `Rollback` ничего не делает.
- Репозиторий на каждом вызове достаёт исполнителя из контекста (`getExecutor`):
  есть транзакция - работает через неё, нет - через пул. Транзакция аргументом
  не передаётся, бизнес-код про pgx не знает.
- Вызов репозитория вне `Do` просто идёт через пул, без транзакции.
- Вложенный `Do` видит транзакцию в контексте и выполняет `fn` в ней, вторую не открывает.
  `COMMIT` и `ROLLBACK` делает только внешний `Do`.

Создание поездки - один `Do`: `INSERT` в `trips` и `INSERT` в `trip_status_history`.
Завершение - тоже один `Do`: условный `UPDATE` и запись в журнал. Атомарность проверена:
при искусственно сломанной второй вставке в `trips` ничего не остаётся.

### Запрет двух активных поездок у водителя

Частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX idx_one_active_trip_per_driver
    ON trips (driver_id)
    WHERE status = 'active';
```

Уникальность действует только среди активных поездок, завершённых у водителя может
быть сколько угодно. Проверку делает сама база в момент вставки, поэтому гонки нет:
из параллельных `INSERT` пройдёт один, остальные получат ошибку `23505`, которую
репозиторий превращает в доменную `ErrDriverBusy`, а хендлер - в `409 driver_busy`.
Проверка `SELECT` перед `INSERT` так не работает: оба запроса успеют проверить раньше,
чем любой из них вставит строку.

Проверено: 20 параллельных создания на одного водителя дают ровно один 201 и 19 ответов 409.

### Завершение поездки при конкурентных запросах

Статус проверяется прямо в `UPDATE`:
`UPDATE trips SET status='completed', ... WHERE id = $1 AND status = 'active'`.
Первый запрос блокирует строку, второй ждёт его коммита, а затем перепроверяет условие.
Статус уже `completed`, строка не подходит, затронуто 0 строк. Тогда дополнительное
чтение по `id` различает случаи: строки нет - `404`, строка есть - `409 trip_completed`.
`finished_at` не перезаписывается. Проверено: два параллельных `finish` дают один 200 и один 409.

### Валидация тела запроса

Стандартный `encoding/json` подставляет нули вместо отсутствующих полей, сопоставляет
ключи без учёта регистра и не замечает данные после первого JSON-объекта. Поэтому тело
`POST /api/v1/trips` разбирается в несколько шагов:

1. Тело читается целиком, размер ограничен 1 МБ.
2. Тело разбирается в `map[string]json.RawMessage`: `json.Unmarshal` требует ровно одно
   JSON-значение, поэтому мусор после объекта даёт ошибку. Ключи сверяются с допустимыми
   по точному совпадению, на верхнем уровне и внутри `start_point`/`end_point`.
   Так отклоняются лишние поля и ключи в другом регистре (`USER_ID`, `LATITUDE`).
3. Тело разбирается в структуру, где все поля - указатели. Отсутствующее поле и `null`
   оставляют указатель `nil`, и это отличается от законного нуля (`price: 0`).
4. Каждое обязательное поле, включая координаты обеих точек, проверяется на `nil`.
5. Значения проверяются на допустимость: непустые UUID, диапазоны координат, `price >= 0`.

Любая ошибка - `400 invalid_request` с указанием поля в `detail`. Внутренние подробности
(имена Go-типов, текст библиотек) в ответ не попадают.

### Graceful shutdown

По `SIGINT`/`SIGTERM` создаётся один контекст на `SHUTDOWN_TIMEOUT`, общий для всего
завершения:

1. `server.Shutdown` - новые запросы не принимаются, текущие дорабатывают.
   Если бюджет кончился - `server.Close()`.
2. Закрытие пула. `pool.Close()` не принимает контекст и ждёт возврата всех соединений,
   поэтому выполняется в горутине, а основной поток ждёт либо его завершения, либо
   истечения того же контекста. Если бюджет кончился - лог и принудительный выход
   с кодом 1.

Сервер останавливается раньше пула, потому что текущим запросам ещё нужна БД.
Если сервер упал сам (например, порт занят), пул закрывается с тем же ограничением,
и процесс выходит с кодом 1.

### Прочее

- Код по OpenAPI генерируется в `internal/generated/` (пакет `api`), как в команде
  из задания, а не в `api/` из общей структуры. Генерация ограничена операциями этой работы.
- `/health` не ходит в базу: это liveness, упавшая БД не должна приводить к рестарту процесса.
  `/ready` делает Ping и отвечает 503, пока база недоступна. Обе ручки отдают `HealthResponse`
  в `application/json`.
- `id` и `started_at` генерирует сервис, из запроса они не принимаются.

## Известные упрощения

- Логика оркестрации лежит в хендлерах, отдельного слоя service нет - по заданию
  работа пишется прямолинейно, слои появятся в работе 2.
- Репозиторий передаётся конкретным типом, интерфейсы и моки - в работе 2.
- Тестов нет, логирование через `fmt.Println` вместо `slog` - в работе 2.
- Идемпотентность и Dockerfile (задания со звёздочкой) не сделаны.
